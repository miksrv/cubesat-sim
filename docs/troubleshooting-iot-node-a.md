## 1. Топология I2C-шины

Обе платы (Sense HAT C и IoT Node(A)) стоят одновременно на одной шине I2C-1.

Полный скан адресов (после включения overlay, когда `0x48` занят драйвером):

| Адрес | Устройство | Источник |
|---|---|---|
| `0x0c` | AK09918C (магнетометр) | Sense HAT C |
| `0x16` | LoRa-модуль / управление A9G (см. §3) | IoT Node(A) |
| `0x29` | TCS34725 (цвет, не используется) | Sense HAT C |
| `0x36` | X728 fuel gauge | UPS HAT |
| `0x48` | **SC16IS752** (UART-мост A9G) | IoT Node(A) — занят драйвером после overlay |
| `0x5c` | LPS22HB (барометр) | Sense HAT C |
| `0x68` | DS1307 RTC | UPS HAT |
| `0x6b` | QMI8658C (IMU) | Sense HAT C |
| `0x70` | SHTC3 (влажность) | Sense HAT C |

**Обновление: конфликт адреса `0x48` подтверждён экспериментально (без разборки).**

Документация `docs/hardware-sense-hat-c.md` указывает адрес `0x48` для ADC SGM58031 (Sense HAT C, не используется проектом) — тот же адрес, что и у SC16IS752. Провели прямой тест стабильности без физического разделения плат:

**Методика:** временно отвязали драйвер ядра от устройства (`echo '1-0048' | sudo tee /sys/bus/i2c/drivers/sc16is7xx/unbind`), что снимает `/dev/ttySC0`/`/dev/ttySC1` и открывает прямой доступ к адресу `0x48` через `smbus2`. Тестировали scratchpad-регистр SC16IS752 (SPR, `reg = (0x07<<3)|(0<<1) = 0x38`) — это регистр общего назначения без побочных эффектов, чтение/запись должны быть 100% детерминированы на исправном одиночном чипе.

**Результат:**
- **100 итераций записи разных байт + немедленное чтение обратно: 85 несовпадений из 100.** Паттерн искажений **зависит от конкретных записываемых бит** (разные биты "теряются" по-разному для разных значений) — не фиксированная маска.
- **Контрольный тест:** записали `0x5A` один раз, затем прочитали тот же регистр 20 раз **без единой новой записи** — все 20 чтений вернули **одно и то же значение `0x1A`**, без единого отклонения.

**Интерпретация:** чтение стабильно и воспроизводимо, а искажается именно запись, причём data-dependent (не константная маска). Это классическая сигнатура двух устройств, конкурирующих за одну адресную линию I2C (open-drain — если второе устройство в момент записи бита "1" тянет SDA в "0", наш бит "проигрывает"; какие биты потеряются — зависит от того, что в этот момент передаёт второе устройство). Случайный шум/наводки обычно давали бы нестабильность и на чтении тоже — а у нас чтение железно стабильно.

**Но:** попытка подтвердить, что второе устройство — именно SGM58031 (ADS1115-совместимый ADC), **не удалась**. Проверяли характерные для ADS1115-семейства регистры (pointer-адресация: конфиг-регистр `0x01`, конверсия `0x00`) — получили статичные `0x0000` на обоих, 8 повторных чтений конверсии без единого "дрожания". Настоящий работающий ADC почти наверняка показал бы: (а) нестандартный дефолт конфиг-регистра (у ADS1115 обычно `0x8583`, не `0x0000`), (б) хоть какой-то шум на конверсии от цикла к циклу. Плоский `0x0000` — это либо неактивный/неисправный ADC, либо мы просто попали в "непротокольный" доступ к самому SC16IS752 (адресация ADS1115 через pointer-регистр отличается от адресации SC16IS752 через `(reg<<3)|(ch<<1)`), и результат ничего не говорит о присутствии второго чипа.

**Итог: конфликт на адресе `0x48` подтверждён (запись искажается детерминированно-непредсказуемо), но конкретный виновник (SGM58031 или что-то другое) — не идентифицирован.** Косвенно это может объяснять и молчание GPS, и раннюю странность с регистрами `0x16` (см. §3) — если I2C-шина в принципе нестабильна из-за конкуренции адресов где-то на ней, это может влиять на несвязанные транзакции тоже.

**Побочный технический момент:** `unbind`/`bind` через sysfs для этого устройства **не работает чисто** — после `unbind` попытка `bind` дважды провалилась (`dmesg`: `probe with driver sc16is7xx failed with error -22`, `irq: type mismatch, failed to map hwirq-24`). Требуется **полная перезагрузка**, чтобы аккуратно восстановить `/dev/ttySC0`/`/dev/ttySC1` — динамическая привязка не переинициализирует IRQ-ресурсы так же чисто, как загрузка device tree при старте системы. Если нужно повторить этот тест в будущем — учитывать, что понадобится ребут после.

## 2. GPS / GSM (модуль A9G) — не работает

### Что настроено верно
- `dtoverlay=sc16is752-i2c` в `/boot/firmware/config.txt` — **дефолтный адрес `0x48` подтверждён правильным** (расшифровка вендорского `.dtbo` через `dtc` показала тот же `reg=0x48`, `interrupts=<0x18 0x02>` = GPIO24, что и в стоковом overlay Raspberry Pi OS — вендорский файл 2019 года просто дублирует то, что сейчас есть "из коробки").
- После ребута создаются `/dev/ttySC0` (AT-команды/GSM) и `/dev/ttySC1` (NMEA/GPS).
- Команда сброса модуля `i2cset -y 1 0x16 0x23 0x40` (из вики вендора) отправляется без ошибок I2C.
- `gpsd` + `gpsd-clients` установлены, `/etc/default/gpsd` настроен (`DEVICES="/dev/ttySC1"`), сервис стартует и корректно открывает порт на 9600 8N1.
- Питание в норме: `vcgencmd get_throttled` = `0x0`, нет undervoltage-предупреждений в `dmesg`.

### Результат тестов — стабильно отрицательный
- **`ttySC1` (GPS/NMEA):** 0 байт на всех скоростях (4800–115200), при прямом чтении (`cat`) и через `gpsd -D 5` (35 секунд ожидания). Абсолютная тишина, не мусор — то есть физически ничего не приходит на линию.
- **`ttySC0` (AT/GSM):** **любая** запись (raw termios, `cat`, `pyserial`, команда сброса из демо-скрипта вендора `AT+GPS=1`) **стабильно (3/3) вешает поток обработки прерывания ядра** `irq/47-1-0048` в состоянии `D` (uninterruptible sleep, не убивается `kill -9`). Зависание видно в `dmesg`:
  ```
  INFO: task cat:XXXX blocked for more than 120 seconds.
  ... synchronize_irq → uart_port_shutdown → uart_close ...
  ```
  Каждое такое зависание требует **полной перезагрузки** Pi (мягкая `sudo reboot` срабатывает, но занимает ~90–190 секунд вместо обычных ~30).

### Гипотеза причины
Драйвер `sc16is7xx` работает в режиме прерываний (GPIO24 = `int_pin`, дефолт overlay). При `write()`, ожидающем прерывания "TX FIFO opened", если реальный вывод INT чипа физически не подключен к GPIO24 на этой ревизии платы (или подключен к другому пину) — прерывание никогда не приходит, и поток `irq/47-1-0048` виснет навсегда. Воспроизводится независимо от контента команды — только от самого факта записи.

52Pi wiki **не документирует**, к какому GPIO подключен INT — без этого нельзя подобрать правильный `int_pin` параметр удалённо.

### Не подтвердившиеся гипотезы
- ~~Overlay привязался не к тому чипу (адрес 0x48 вместо 0x16)~~ — опровергнуто: `0x48` подтверждён вендорским `.dtbo` как правильный дефолт.
- ~~Документация перепутала порты (GPS на ttySC0, а не ttySC1)~~ — опровергнуто: полная развёртка (оба порта × 6 скоростей, чисто на приём) дала тишину везде, ни на одном порту нет несанкционированного NMEA-потока.
- Отсутствие SIM-карты — не должно влиять на GPS (по документации A9G, "GPS works standalone, no SIM needed"); маловероятная причина зависания IRQ (тот баг чисто программный/kernel-level).

### Новая гипотеза (частично подтверждена): конфликт адреса `0x48`
См. §1 — прямой тест scratchpad-регистра показал детерминированно-непредсказуемое искажение записи на адресе `0x48`, характерное для двух устройств на одной адресной линии. Это может объяснять как молчание GPS/AT-портов, так и зависание IRQ-потока при записи в `ttySC0` — если I2C-транзакции к мосту искажаются на уровне записи, драйвер может застревать в непредвиденном состоянии при ожидании корректного ACK/статуса. Виновник конфликта (SGM58031 на Sense HAT C или что-то иное) **не идентифицирован окончательно** — попытка отличить поведение ADC не дала однозначного подтверждения (см. §1).

### Дальнейшие шаги (нужны физически)
1. Мультиметром проверить напряжение непосредственно на выводах модуля A9G (не на плате в целом).
2. Проверить целостность пайки UART-линий между SC16IS752 и A9G.
3. Проверить, не перепутаны ли антенные разъёмы GPS/GSM (если на плате два похожих разъёма).
4. Написать в поддержку 52Pi: чип-мост отвечает и идентифицируется корректно, `i2cset` reset уходит без ошибок, но AT-порт вешает IRQ-поток ядра при любой записи, NMEA-порт полностью молчит — попросить точную схему GPIO для INT-пина модуля.

## 3. LoRa — передаёт в эфир, но неправильно промодулирован

### Найденное несоответствие в коде проекта

Реальная регистровая карта (по вики вендора, подтверждена точным демо-кодом) **отличается** от того, что реализовано в `src/comms/lora.py`:

| | Код проекта (`lora.py`) | Реальное железо (вики + демо-код) |
|---|---|---|
| TX данные | `0x02`–`0x1F` (после байта длины на `0x01`) | `0x01`–`0x10` (**16 байт, без байта длины!**) |
| RX данные | `0x02`–`0x1F` (общий с TX по логике кода) | `0x11`–`0x20` (**отдельный от TX буфер**) |
| Регистр `0x23` | `0x01`=TX trigger, `0x02`=RX flag (упрощённая трактовка) | Битовое поле: `L_SET`(0x80?) `\| G_RESET`(0x40) `\| reserved \| L_RXNE`(0x02) `\| L_TX`(0x01) — совпадает по битам `0x01`/`0x02`, но `0x40` — это **общий reset модуля** (тот самый из инструкции по сбросу A9G), а не что-то LoRa-специфичное |
| Регистр `0x22` | Не используется | `Band range(7-12) \| Spread bandwidth(6-9) \| Data ratio(1-4)`, дефолт `0x0B` — **не задокументирован по битам точно**, вендор рекомендует "оставить дефолт" |

**Следствие:** текущий `LoRaModule.send()` пишет байт "длины" в `0x01` (реально первый байт TX-буфера железа) и сдвигает полезные данные на `0x02`, из-за чего первый байт данных теряется/искажается, а запись, доходящая до `0x1F`, выходит за границу реального TX-буфера (`0x10`) и попадает в RX-буфер (`0x11`–`0x20`), который физически read-only на приём — эти байты, скорее всего, просто отбрасываются железом без ошибки на шине.

### Экспериментальное подтверждение через SDR

Точно по вендорской схеме (без байта длины, 16 байт напрямую в `0x01`–`0x10`, затем `0x23=0x01`) была отправлена серия тестовых пакетов (паттерн `AA 55 A5 5A` × 4). Пользователь наблюдал на SDR (waterfall, диапазон 433–435 МГц):

- **Огромные, чётко коррелирующие по времени всплески** на каждый триггер передачи (10 пакетов, затем контрольно ещё 2 — оба совпали по времени с точностью до секунды).
- **Контрольный эксперимент**: такое же количество I2C-транзакций (17 операций, 2 раза, интервал 3с), но к **не связанному с LoRa адресу** (`0x6b`, IMU) — **ничего** не появилось на водопаде. Это исключает гипотезу "это просто шум от переключений I2C-шины".
- **Вывод: LoRa-чип реально передаёт RF-энергию по триггеру `0x23=0x01`.** Модуль физически жив, в отличие от GSM/GPS-части.

### Проблема: аномально широкая полоса

Наблюдаемый сигнал занимал **~2 МГц** (от ~431 до ~433 МГц по показаниям пользователя) — это **в 4–16 раз шире**, чем ожидаемая полоса реального LoRa-сигнала (125–500 кГц typical для SX127x-подобных чипов).

Вероятные причины (не проверено):
1. Регистр `0x22` (bandwidth/spreading factor) оставлен на заводском дефолте `0x0B`, который может не соответствовать чистой узкополосной LoRa-модуляции — возможно, чип фактически работает в widebandFSK/GFSK режиме, а не в true LoRa chirp-spread-spectrum.
2. Плохое согласование антенны/тракта — может размазывать спектр и создавать гармоники.
3. PLL синтезатора частоты не запирается на целевой частоте (нестабильная генерация) — тоже даёт широкий "плюх" вместо чистой несущей.

### Обновление: регистр `0x22` работает, но требует бита `L_SET`

Точная битовая раскладка `0x22` (по данным вендора, уточнено пользователем):

```
бит:      7         6-4              3-2                1-0
поле:     Reserved  SpreadingFactor  SignalBandwidth     ErrorCoding
          (1 бит)   (3 бита, SF7-12) (2 бита, индекс 6-9) (2 бита, CR 1-4)
```

Раскладка бит `0x23` уточнена: `L_SET`(`0x80`, бит7) `\| G_RESET`(`0x40`, бит6) `\| reserved`(биты 5-2) `\| L_RXNE`(`0x02`, бит1) `\| L_TX`(`0x01`, бит0).

**Подтверждено экспериментально:** просто запись в `0x22` **не действует** на радиочасть, пока не отправлен бит `L_SET` (`0x23 = 0x80`) — видимо, это триггер "применить конфигурацию". После записи `0x22 = 0x53` (сузили `SignalBandwidth` с дефолтного индекса на минимальный в допустимом диапазоне, остальные поля не трогали) и `0x23 = 0x80`:

- **Полоса сигнала на SDR заметно сузилась** (было ~2 МГц, стало намного уже — визуально подтверждено пользователем).
- **Измерена точная несущая частота: 433.990 МГц** (первое точное измерение; вендор указывает только диапазон "433MHz").
- Значение `0x22` **персистентно** между запусками скрипта (не сбрасывается на дефолт сам по себе) — при повторном запуске чтение вернуло уже записанные `0x53`.
- Любопытно: чтение `0x22` **до** первой записи в этой сессии показало `0x00`, а не заявленный вендором дефолт `0x5B` (`0b01011011`) — возможно, наш более ранний `G_RESET` (`0x23=0x40`) сбросил этот регистр в ноль, либо реальный power-on-default отличается от того, что вендор считает "рекомендуемым".

**Обнаружена вторичная проблема — гармоники антенны.** На несогласованной антенне (импровизированный дипольный излучатель из металлической ленты рулетки) при передаче на 433.99 МГц одновременно **зафиксированы помехи на ~868 МГц** — это классическая вторая гармоника (2 × 433.99 = 867.98 МГц, совпадает почти точно). Это указывает на плохое согласование антенны с выходным каскадом передатчика, а не на проблему конфигурации/кода — типичное следствие непроверенного самодельного излучателя без правильной длины/согласования.

### Дальнейшие шаги
1. Исправить `src/comms/lora.py`: убрать байт "длины" на `0x01`, писать данные напрямую в `0x01`–`0x10` (максимум 16 байт полезной нагрузки), читать RX из `0x11`–`0x20` отдельно, и добавить запись `L_SET` (`0x23=0x80`) после изменения `0x22`, перед триггером `L_TX`.
2. Собрать/подключить нормальную антенну — четвертьволновый монополь на 433.99 МГц: λ/4 ≈ **17.3 см** (λ = c/f ≈ 0.691 м). Ожидаемый эффект — заметное снижение гармоник на 868 МГц и рост эффективности передачи.
3. Дальше подбирать биты `SpreadingFactor`/`ErrorCoding` в `0x22` для более узкой/быстрой конфигурации под конкретную задачу (баланс между дальностью и скоростью передачи).
4. Проверить, есть ли смысл держать `G_RESET` и `L_SET` как раздельные шаги при каждой инициализации COMMS-сервиса (сейчас порядок операций эмпирически подтверждён только вручную через тестовый скрипт, не в реальном `lora.py`).

## 4. Общие технические заметки по железу

- Реальный физический адрес UART-моста SC16IS752 — **`0x48`**, а не `0x16` как ошибочно указано в `docs/hardware-iot-node-a-52pi.md` (эту документацию стоит поправить).
- Адрес `0x16` — это **отдельная микросхема/интерфейс** на плате IoT Node(A), отвечающая за (a) reset модуля A9G и (b) регистровый доступ к LoRa-чипу. Это не SC16IS752.
- На Raspberry Pi сейчас развёрнут устаревший код проекта (коммит `4ffd546`, на момент начала сессии), без `src/comms/`, `src/common/gps_a9g.py` и переименования telemetry→COMMS (эти изменения есть в `origin/main`, но не задеплоены). Все `cubesat-*.service` были в состоянии `disabled` на момент диагностики.
- `i2c-tools` не установлен на Pi — все I2C-операции в этой сессии делались через `python3 -c "import smbus2..."` напрямую, без `i2cget`/`i2cset`/`i2cdetect`.
